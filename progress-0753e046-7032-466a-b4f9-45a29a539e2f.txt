## Codebase Patterns
- Project uses ESM (type: "module") with .js imports
- Tests use Jest with `node --experimental-vm-modules` — without the flag, ESM imports fail
- jest.mock() is incompatible with ESM mode; use jest.unstable_mockModule() with top-level await, or write integration tests that exercise the real code path
- Build: `tsc` (TypeScript compiler)
- Supervisor uses bindTools(availableTools[]) for tool-enabled 1st pass, then re-invokes model without bindTools for 2nd-pass synthesis
- bindTools returns a Runnable; invoke() returns AIMessage with optional .tool_calls[] ({name, args, id})
- Heterogeneous tool arrays (different tool types from different modules) cause TS2349 on .invoke() — cast `tool as any` before invoke
- ToolMessage requires tool_call_id matching the original AIMessage tool_call.id
- Skills registry exports SKILL_DEFINITIONS array with SkillDefinition interface
- getSkillCatalogSummary() maps SKILL_DEFINITIONS to "N. id: summary" format
- Workflow uses LangGraph StateGraph with addNode/addEdge/addConditionalEdges
- Test suite requires DEEPSEEK_API_KEY and GROQ_API_KEY env vars to load modules; tests fall through to error recovery paths with fake keys, which validates flow but doesn't exercise LLM logic
- Agents that return {nextAgent, messages, contextData} control flow via workflow routing functions
- LangChain tool() definitions use `tool(async (params) => {...}, { name: "tool_name", schema: z.object({...}) })` pattern
- Agent files export node functions (e.g., searchAgentNode), and tools must be explicitly exported (export const) for external consumption
- Security agent uses 14 distinct tool names for trust management, account management, group ignore, and auto-reply
